## 3. Grill 一致性审计与最终裁决

### 3.1 阻塞级问题

| 编号 | 不一致/缺口 | 风险 | 最终裁决 |
|---|---|---|---|
| A01 | 需求写 SQLite，详细设计写 UniApp Storage | 移动端会形成两套持久化实现 | 已按用户决定更新需求：只使用 UniApp Storage，照片放私有目录，不引入 SQLite |
| A02 | 详细设计要求 73 个接口、28 表，但消息列表和异步消息没有消息表 | M08 消息无法持久化、已读和重试 | 新增 `sys_message`，数据库基线为 29 表；消息写入与业务事务解耦但可追踪 |
| A03 | `wo_repair` 只有待受理/已派单/已驳回，业务又要求“未闭环”和完工闭环 | 删除校验、统计和设备状态无法判断 | 增加状态 3“已关闭”；工单验收成功时关闭报修单 |
| A04 | 工单派发/完工/验收 DTO 需要派单备注、期望完成时间、验收照片，但表中无字段 | 接口数据无法落库 | `wo_order` 增加 `dispatch_remark`、`expect_finish_time`、`accept_images`；完工必须保存 `repair_plan` |
| A05 | 移动端文件上传需要业务 ID，但离线任务明细提交前尚无稳定绑定上下文 | 照片无法先传后交单，易产生悬挂文件 | 上传先返回 `fileId/uploadToken`，`sys_file.biz_*` 可空；业务提交时按文件 ID 绑定，定时清理超期未绑定文件 |
| A06 | 文档称 Token 可全局失效，但只设计了 Redis 黑名单 | 重置口令/禁用账号后旧 Token 仍可能有效 | `sys_user` 增加 `token_version`，JWT 带版本；禁用/重置时递增，退出将当前 `jti` 加黑名单 |

### 3.2 高风险问题

| 编号 | 不一致/缺口 | 最终裁决及实施影响 |
|---|---|---|
| A07 | 二维码格式出现 `EQ:` 与 `WJYS:EQ:` 两种，且建议 MD5 | 统一为 `WJYS:{EQ\|POINT}:{code}:{signature}`；签名使用服务端密钥的 HMAC-SHA256 截断值，不使用 MD5；增加点位二维码接口 |
| A08 | 巡检提交幂等有“全局 submitNo”和“taskId + submitNo”两种说法 | 客户端生成全局唯一 UUID `submitNo`；数据库唯一索引 `uk_submit_no`，`ins_task` 保存 `submit_hash`，同号同载荷返回原结果，同号不同载荷返回 409 |
| A09 | 文档引用 `offline_time`，数据库没有字段 | `ins_task` 增加 `client_submit_time`，服务端另写 `finish_time`；离线标志由请求与时间共同记录 |
| A10 | 任务快照字段不足以离线渲染/校验 | `ins_task_item` 增加设备/点位编码、取值类型、检查方法、单位、选项快照；`ins_item` 增加 `options_json` |
| A11 | 数值越界“自动异常”与“人工正常可覆盖”冲突 | 安全优先：数值越界必为异常，人工只能把正常提升为异常，不能把越界改为正常；异常必须说明 |
| A12 | 一个计划可含多个设备，但“按设备责任人派发”只有一个 assignee | 启用计划前校验所有点位对应同一责任人；否则要求固定人员/班组。当前不拆分任务，以保持 `(plan_id, plan_time)` 唯一性 |
| A13 | 设备删除校验混用了任务和工单状态数字 | 分表判断：任务活跃 `0/1/3`，工单活跃 `0/1/2/4`，报修活跃 `0/1`；任一存在即拒绝删除 |
| A14 | 维保文档同时说“归档只读”和“管理员退回归档后重提” | 已归档 `status=1` 永久只读；只有已退回 `status=2` 可修改后重新提交。归档纠错新增更正记录，不原地篡改 |
| A15 | `mt_record` 业务要求同计划同日唯一，索引表未定义 | 新增唯一索引 `uk_mt_record_plan_date(plan_id, maintain_date)`；`plan_id` 为空的临时记录不受该唯一约束 |
| A16 | Redis 分布式锁只写“解锁”，没有所有权检查 | 锁值使用随机 token，Lua 比较 token 后删除；任务生成同时依赖数据库唯一索引兜底 |

### 3.3 中风险与规范问题

| 编号 | 问题 | 裁决 |
|---|---|---|
| A17 | 详细设计称“全部逻辑删除”，但大部分表没有 `deleted` | 主数据/配置表可逻辑删除；业务单据、日志、库存流水不删除，只通过状态关闭。迁移按表明确，不机械增加全表 `deleted` |
| A18 | 文件表同时保存 `file_path` 和长期 `file_url` | 只以 `object_key` 为权威位置；URL 临时签发，不持久化带时效的访问 URL |
| A19 | 多个业务表用逗号拼接照片 URL | 新代码统一通过 `sys_file(biz_type,biz_id)` 关联；DTO 使用 `fileIds`。旧 `images/photo_urls` 字段不作为新实现真源 |
| A20 | 设备报修允许多开，与“重复报修合并”冲突 | 同设备同一时刻只允许一个活跃报修/工单；事务内加设备维度锁并再次查询。历史脏数据存在时，全部活跃工单关闭后才恢复设备状态 |
| A21 | API 文档提到版本化，但路径均为 `/api` | 本期保持 `/api`，避免同时维护 `/api/v1`；只有破坏性升级时引入 `/api/v2` |
| A22 | 错误响应可能全部 HTTP 200 | HTTP 层使用 400/401/403/404/409/429/500；响应体仍采用统一业务 `code/message/data/traceId` |
| A23 | 后端包名示例在 `com.wjys.module.*` 与 `com.wjys.inspection` 间摇摆 | 统一为 `com.wjys.module.<domain>`；共享设施只在 `common/security/support` |
| A24 | 看板示例 SQL 未完整计算 MTBF/MTTR/健康分 | 日统计任务显式计算并 upsert；接口读取聚合表，支持实时小范围回补；公式必须有单测 |
| A25 | 移动端静默刷新被描述，但没有刷新接口 | 增加 `POST /api/auth/refresh`，使用轮换 refresh token；Web 与移动端统一认证协议 |

### 4.2 为什么不选 SQLite

本项目离线范围是个人待办快照、少量表单草稿和提交队列，不需要移动端复杂关联查询。采用 SQLite 会引入表结构迁移、原生插件兼容、双数据库模型和额外测试矩阵。UniApp Storage 足以承载结构化小数据，照片移出 Storage 后可控制容量。若未来出现“数万条历史记录离线检索、多账号数据隔离、复杂本地查询”三个条件之一，再通过仓储接口替换为 SQLite，而不是现在提前引入。

### 4.3 Storage 键与容量策略

| 键 | 内容 | 保留策略 |
|---|---|---|
| `wjys:auth:v1` | access/refresh token 元数据 | 退出或失效立即清理 |
| `wjys:user:v1` | 当前用户、角色、权限快照 | 登录刷新，可重建 |
| `wjys:dict:v1:{type}` | 字典缓存 | LRU，可优先清理 |
| `wjys:task:v1:{taskId}` | 待办任务及完整巡检项快照 | 完成同步后可清理 |
| `wjys:draft:v1:{biz}:{id}` | 表单草稿 | 用户完成或主动放弃前保留 |
| `wjys:sync:v1:index` | 待同步记录 ID 有序索引 | 未同步不得清理 |
| `wjys:sync:v1:{submitNo}` | 请求体、摘要、重试状态 | 服务端确认并超过保留期后清理 |
| `wjys:meta:v1` | schemaVersion、容量估算、最后同步游标 | 长期保留 |

每次写入前估算序列化字节数。达到预警线（建议 8 MB）时依次清理过期字典、已完成任务快照、已确认队列；达到硬线前仍不能删除未确认队列和草稿，而是禁止继续下载非必要缓存并提示用户联网同步。照片只在应用私有目录保存路径与校验值，不把 Base64 放入 Storage。

## 5. 总体架构、模块边界与依赖

```text
Web 管理端 / UniApp 移动端
          │ HTTPS + JWT / WebSocket
          ▼
Controller（协议、校验、权限）
          ▼
Application Service（用例编排、事务、状态机）
          ▼
Mapper / Redis / MinIO / Message / Scheduler
          ▼
MySQL 8 + Redis 7 + MinIO
```

模块依赖只允许沿以下方向，不允许循环依赖：

```text
M01 系统基础 ───────────────┐
M02 设备台账 ───────────┐   │
M03 巡检 ──> M02/M01    │   │
M04 维修 ──> M03/M02/M01│   │
M06 备件 ──> M04/M01    │   │
M05 维保 ──> M02/M04/M01│   │
M07 看板 ──> M02~M06（只读聚合）
M08 移动协同 ─> M01/M03/M04/M05（适配层，不复制业务）
Support 文件/消息/WebSocket 被各业务模块调用
```

跨模块调用通过公开 Service 接口或领域事件，禁止直接调用其他模块 Mapper。M08 只编排现有 Service，不建立第二套巡检/维修规则。

## 7. 公共接口与数据库契约

### 7.1 HTTP 约定

- 基础路径：`/api`；JSON 使用 camelCase，数据库使用 snake_case。
- 成功体：`{ "code": 200, "message": "success", "data": ..., "traceId": "..." }`。
- 分页：请求 `pageNum/pageSize`，响应 `data.list/data.total/data.pageNum/data.pageSize`；`pageSize` 最大 200。
- 写接口必须校验权限和数据范围；前端权限仅控制展示。
- 时间字段传 ISO 8601；客户端离线时间单独命名 `clientSubmitTime`，不能覆盖服务端审计时间。
- `Idempotency-Key` 可与体内 `submitNo` 同值；服务端二者同时存在时必须一致。
- 列表查询只返回展示字段；详情接口才返回日志、照片等重对象。

### 7.2 数据库基线（29 表）

| 域 | 表 | 写入边界 |
|---|---|---|
| M01 | `sys_user/sys_role/sys_user_role/sys_menu/sys_role_menu/sys_dept/sys_dict/sys_oper_log` | 系统管理事务 |
| Support | `sys_file/sys_message` | 文件绑定、消息持久化 |
| M02 | `eq_category/eq_equipment/eq_param/eq_status_log` | 设备档案与状态履历同事务 |
| M03 | `ins_point/ins_item/ins_plan/ins_plan_point/ins_task/ins_task_item/ins_abnormal` | 任务提交和异常生成同事务 |
| M04 | `wo_repair/wo_order/wo_order_log` | 受理、派工、完工、验收状态机 |
| M06 | `wo_spare/wo_spare_record` | 库存原子扣减与消耗流水同事务 |
| M05 | `mt_plan/mt_record` | 记录审核与下次日期推进同事务 |
| M07 | `stat_equip_daily` | 调度聚合 upsert |

### 7.3 相对原详细设计的迁移修订

- `sys_user`：增加 `token_version int not null default 0`。
- `sys_file`：`file_path` 改语义为 `object_key`，增加 `upload_token`、`bind_status`、`checksum`、`expire_time`；不保存临时 URL。
- 新增 `sys_message`：`id,user_id,type,title,content,biz_type,biz_id,read_flag,push_status,retry_count,created_time,read_time`，索引 `(user_id,read_flag,created_time)`。
- `ins_item`：增加 `options_json`。
- `ins_task`：增加 `client_submit_time`、`submit_hash`，保留 `submit_no` 全局唯一。
- `ins_task_item`：增加 `equip_id/equip_code/point_code/value_type/check_method/unit/options_json` 快照字段；照片通过 `sys_file` 绑定。
- `wo_repair.status`：增加 3 已关闭。
- `wo_order`：增加 `dispatch_remark/expect_finish_time/accept_images`。
- `mt_record`：增加 `uk_mt_record_plan_date(plan_id,maintain_date)`。
- 所有主表补充 `created_time/updated_time/version` 中确有并发/审计需要的字段；日志、流水表不做逻辑删除。

## 8. 模块实施说明

### 8.1 M01 系统与基础数据

**边界**：认证、刷新/退出、用户、角色、菜单、部门、字典、操作日志、数据权限。它不包含设备/巡检业务规则。

**后端核心类与方法**：

- `AuthController`：`login(LoginDTO)`、`refresh(RefreshTokenDTO)`、`logout()`、`info()`。
- `AuthService`：`TokenPair login(...)`、`TokenPair refresh(...)`、`void logout(jti)`。
- `UserService`：`page(UserQuery)`、`create(UserCreateDTO)`、`update(id,...)`、`resetPassword(id,...)`、`delete(id)`；禁用/重置递增 `tokenVersion`。
- `RoleService`：保存角色和菜单关系时先校验菜单存在、状态有效，并在单事务重建关联。
- `DataScopeService`：根据角色范围返回本人/部门树/全部条件，由 Mapper SQL 显式消费。

**Web**：登录页、用户/角色/部门/字典/日志页面；`auth` 和 `permission` Store；动态菜单转路由；按钮使用 `v-permission`。

**接口**：保留详细设计 1～14，新增 `POST /api/auth/refresh`；用户禁用采用 `PUT /api/system/users/{id}/status`，避免用删除表达停用。

**数据与测试**：验证 BCrypt、Token 版本失效、刷新轮换、角色菜单事务、数据范围、401/403、敏感日志脱敏。M02～M08 开发前 M01 必须稳定。

### 8.2 M02 设备档案台账

**边界**：分类、设备主数据、技术参数、二维码、状态履历。状态变化必须走 `EquipmentStatusService`，其他模块不得直接更新 `eq_equipment.status`。

**核心方法**：

- `EquipmentService.create/update/detail/page/delete`。
- `EquipmentStatusService.changeStatus(equipId,target,sourceType,sourceId,reason)`：校验转换并写 `eq_status_log`。
- `EquipmentQrService.generateEquipmentQr(id)`、`generatePointQr(pointId)`、`parseAndVerify(payload)`。
- 删除前分别查询活跃巡检任务、工单和报修，任一存在返回 409。

**Web**：设备列表/详情、分类树、参数编辑、状态履历时间线、二维码下载。

**接口修订**：详细设计 15～25 保留；点位二维码由 M03 增加 `POST /api/inspection/points/{id}/qrcode`；扫码参数放查询体或 URL 编码，不能直接信任二维码明文。

**联调**：M03 通过设备/点位读取快照，M04/M05 只经状态服务切换故障/维修/保养状态，M07 读取设备维度。测试唯一编码、非法状态、二维码篡改和删除冲突。

### 8.3 M03 巡检计划与任务

**边界**：点位、巡检项、计划、调度生成、领取、执行、幂等提交、异常闭环。计划修改不改变已经生成的任务快照。

**核心方法**：

- `InspectionPlanService.create/update/changeStatus/generateNow`。
- `TaskGenerateService.generate(planId,planTime)`：Redis token 锁 + `uk_plan_time` 双保险；生成任务与完整项目快照同事务。
- `InspectionTaskService.receive(taskId,userId)`：条件更新 `0 -> 1`。
- `InspectionSubmitService.submit(taskId,TaskSubmitDTO)`：允许 `1/3 -> 2`；校验执行人、完整项、扫码点位、必拍、范围、幂等；更新明细、异常、任务统计和文件绑定。
- `AbnormalService.toRepair(abnormalId,...)`：调用 M04 的公开报修服务，来源唯一约束防重复。

**提交参数**：`submitNo/clientSubmitTime/offlineFlag/items[]`；item 含 `taskItemId/checkResult/checkValue/remark/checkTime/fileIds[]`。服务端重新计算越界，不信任客户端异常结论。

**Web**：点位/项目配置、计划列表与编辑、任务监控、异常列表、统计页面。

**移动端**：任务拉取后保存完整快照；执行时扫码核对点位；离线写草稿和队列；重试沿用同一 `submitNo`。

**测试**：计划月末、周周期、跨时区边界、重复调度、并发领取、越界强制异常、必拍、离线重复提交、同幂等号不同载荷、超时后补交、异常转报修。

### 8.4 M04 故障报修与维修

**边界**：报修、受理/驳回、派工、接单、完工、验收/退回、工单日志。库存由 M06 负责，设备状态由 M02 负责。

**状态机**：

- 报修：`0 待受理 -> 1 已派单 -> 3 已关闭`，或 `0 -> 2 已驳回`。
- 工单：`0 待接单 -> 1 维修中 -> 2 待验收 -> 3 已完成`；验收退回 `2 -> 4 -> 1`。

**核心方法**：

- `RepairReportService.create/accept/reject`：设备维度锁内检查活跃单据。
- `WorkOrderService.dispatch(DispatchDTO)`：写派工信息、日志、消息，设备转维修中。
- `start(id)`：仅指定维修人可接单，条件更新。
- `finish(id,FinishDTO)`：保存原因、方案、结果、停机时长和文件。
- `accept(id,AcceptDTO)`：关闭工单与报修、关闭来源异常、更新设备状态、发出统计事件。
- `reject(id,RejectDTO)`：待验收退回并记录原因。

**Web/移动端**：报修单管理、工单列表/详情/流程时间线；移动端支持报修、接单、完工和照片。验收仍由有权限的管理端或移动端人员执行。

**联调/测试**：与 M02 状态、M03 异常、M06 库存、M07 指标、消息中心联动；覆盖重复报修、越权接单、并发状态更新、验收回滚、历史多活跃单据。

### 8.5 M05 维保管理与归档

**边界**：保养计划、到期提醒、维保记录、审核归档、设备履历。归档记录不可改写。

**核心方法**：

- `MaintenancePlanService.create/update/changeStatus`。
- `MaintenanceRecordService.submit`：同计划同日唯一，绑定文件；异常结果可调用 M04 报修。
- `audit(id,AuditDTO)`：通过则 `0 -> 1` 并推进 `next_date`；退回则 `0 -> 2`。
- `resubmit(id,...)`：只允许 `2 -> 0`；`1` 永远只读。

**Web/移动端**：计划页、记录提交/审核/履历；移动端保存草稿并离线同步。设备进入保养中和恢复必须通过 M02 状态服务。

**测试**：重复记录、退回重提、归档不可改、月末周期、审核与计划日期事务回滚、异常转报修。

### 8.6 M06 备件管理

**边界**：备件主数据、库存预警、维修工单领用与流水。首期不实现采购/入库全流程，初始库存和调整需审计权限。

**核心方法**：

- `SpareService.page/create/update/alerts/adjustStock`。
- `SpareConsumptionService.consume(orderId,List<SpareUseDTO>)`：校验工单状态，执行 `stock_qty >= use_qty` 条件更新，写流水，汇总工单 `spare_cost`。
- 同工单同备件再次登记时必须明确追加而非覆盖；撤销采用反向流水，不删除历史记录。

**Web**：备件列表、编辑、预警、库存调整、工单领用弹窗。

**测试**：并发超卖、负数/零数量、停用备件、金额精度、事务回滚和预警边界。

### 8.7 M07 统计分析与决策看板

**边界**：只读聚合、日统计、缓存和导出；不修改业务单据。

**核心方法**：

- `StatisticsJob.aggregate(date)`：按设备 upsert `stat_equip_daily`。
- `DashboardService.overview/trend/pareto/ranking/inspectionSummary`。
- `DashboardExportService.export(query)`：EasyExcel 流式生成并限制时间范围。

**指标**：巡检完成率、异常数、已受理故障数、停机分钟、MTBF、MTTR、健康分。驳回报修不计故障；统计口径、分母为零策略和时区写入 `docs/db/数据字典.md`。

**Web**：总览卡片、故障趋势、Pareto、高频设备、巡检执行分析、筛选和导出。

**测试**：固定样本验证公式、空数据、跨日边界、权限数据范围、缓存失效、导出行数与字段。

### 8.8 M08 移动端协同

**边界**：移动体验与同步适配，不复制 M03/M04/M05 规则。服务端 `MobileSyncService` 调用对应公开 Service。

**接口**：保留详细设计 70～73；`sync/pull` 接收 `cursor,lastSyncTime,modules`，返回任务/字典/消息增量和新 cursor；`sync/push` 接收批次，每条独立返回 `submitNo,status,bizId,errorCode`；上传返回 `fileId/uploadToken/checksum`；新增消息已读接口 `PUT /api/mobile/messages/{id}/read`。

**同步流程**：

1. 在线拉取后原子替换对应任务快照，再更新 cursor。
2. 离线操作先写草稿，再创建固定 `submitNo` 的队列记录。
3. 照片先留私有目录；联网时上传并把 fileId 写回请求体。
4. push 成功后标记 confirmed；409 冲突进入人工处理；网络/5xx 指数退避；参数错误停止自动重试。
5. confirmed 超过保留期后才删除队列和本地照片。

**测试**：断网启动、网络抖动、上传一半退出、重复 push、Token 刷新失败、8/10 MB 容量、扫码篡改、应用重启恢复和多账号切换清理。

## 11. 依赖与环境变更说明

### 11.1 本轮选择“改环境”而非“改文档”的部分

Spring Boot、MyBatis-Plus、Vue/Vite、Element Plus、Pinia、ECharts 等版本在概要/详细设计中已经相互一致，而脚手架依赖偏新或缺失。直接把工程依赖对齐文档的成本较低，也能降低后续 API 变化，因此已修改 `pom.xml`、`package.json` 和 `vite.config.js`。

### 11.2 本轮选择“改文档/裁决”而非“照搬实现”的部分

- 移动存储：详细设计更适合当前体量，故更新需求为 UniApp Storage。
- 消息表、Token 版本、工单缺字段、任务快照和索引：原设计无法支撑已写明的功能，故以本计划修订数据模型，而不是实现不可落库的接口。
- MD5 二维码、长期文件 URL、逗号拼照片：存在安全或维护风险，按改进方案实现。
- 工程目录名：改名收益低、连带成本高，故保留实际目录并统一制品标识。

任何后续依赖新增都要在此追加版本、用途、替代方案和许可证/体积影响。

## 12. 风险、待确认项与控制措施

| 风险 | 控制措施 |
|---|---|
| UniApp Storage 实机容量/厂商差异 | 8 MB 提前预警、照片外置、真机矩阵；仓储接口便于未来替换 |

| 统计口径争议 | 数据字典固定公式，黄金样本单测，产品验收前冻结 |
| 照片悬挂/泄露 | 临时上传 token、绑定状态、超期清理、短期签名 URL、权限校验 |

首期默认不包含采购入库、复杂班次排班、工作流引擎、地图定位和多租户；若新增，必须单独做需求、表结构和阶段评估，不能塞入现有模块。
