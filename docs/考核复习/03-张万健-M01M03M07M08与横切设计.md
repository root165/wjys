# 张万健：M01、M03、M07、M08 与横切设计复习

> 先阅读 [`00-系统公共能力复习.md`](00-系统公共能力复习.md)。你的负责面最广，考场策略是先说模块边界，再挑“认证、巡检提交、移动同步、统计聚合”四个真实实现点展开。

## 1. 我的模块图与答辩定位

```text
M01 认证/RBAC/数据范围 ────所有模块的访问基础
                 │
M03 巡检配置/计划/任务/异常 ─> M04 报修 ─> M06 备件
                 │                     ↑
M08 移动端离线同步（只适配，不复制 M03/M04/M05 规则）
                 │
M07 统计看板：从 M02~M06 只读聚合、缓存与导出
```

- **M01** 决定“谁能做什么、能看什么”；没有它，业务模块没有可信边界。
- **M03** 是现场数据入口，连接设备、异常与维修，是系统最关键的业务闭环起点。
- **M07** 将过程数据转成管理决策指标，但严格只读。
- **M08** 处理弱网现场，保证移动端重试不会重复产生业务数据。
- 横切设计负责事务、幂等、异常响应、Redis 缓存/锁、前端请求和部署一致性。

## 2. M01：认证、RBAC、数据范围

### 2.1 数据与关系

`sys_user`、`sys_role`、`sys_user_role`、`sys_menu`、`sys_role_menu`、`sys_dept`、`sys_dict`、`sys_oper_log` 是基础表。用户与角色、角色与菜单均为多对多；角色带数据范围，菜单同时用于动态路由和接口权限表达。

关键字段：`sys_user.token_version`。禁用用户或重置密码时递增该值，旧 Token 失效；这比只删除前端 Token 更可靠。

### 2.2 核心代码入口

- `module/system/controller/AuthController.java`：`/api/auth/login`、`refresh`、`logout`、`info`、资料/密码接口。
- `AuthService.java`：密码校验、Token Pair 签发、刷新轮换、登出失效。
- `UserService.java`、`RoleService.java`：用户/角色/菜单关联事务；`RoleService.updateMenus` 先验证菜单有效，再删除旧关联、批量写新关联。
- `security/`：JWT 解析、认证上下文、`@PreAuthorize`；`common/`：统一响应、全局异常、分页、审计。
- Web：`frontend/src/api/auth.js`、`stores/auth.js`、`router/index.js`；动态菜单转路由，按钮用 `v-permission`，但后端仍是最终授权边界。

### 2.3 登录输入输出与异常

输入 `LoginRequest`（账号、密码等），`AuthService.login` 查用户、校验启用状态与 BCrypt 密码、加载角色/权限，签发 access/refresh Token。响应 `TokenPairVO`；前端保存登录态并按权限生成路由。

- 密码错误、账户禁用：认证失败；不在日志中记录口令或完整 Token。
- access Token 过期：调用 refresh；刷新 Token 轮换，失效/退出后不能再用。
- 只有隐藏前端按钮但直接调用接口：`@PreAuthorize` 拒绝，返回 403。
- 角色改菜单：在一个事务中重建 `sys_role_menu`，避免半更新。

## 3. M03：巡检计划、任务、提交与异常

### 3.1 核心表和为什么要快照

| 表 | 用途 |
| --- | --- |
| `ins_point`、`ins_item` | 点位和检查项规则 |
| `ins_plan`、`ins_plan_point` | 计划和其包含点位；含周期、执行时间、派发方式 |
| `ins_task` | 某一计划日的一次执行实例，含 `assignee_id,status,submit_no,submit_hash` |
| `ins_task_item` | 任务生成时的检查项快照，含设备/点位/值类型/方法/单位/选项等 |
| `ins_abnormal` | 提交时形成的异常，后续可唯一转 M04 报修 |

计划是可变“规则”，任务是不可被后续配置篡改的“历史执行实例”。因此任务生成时必须快照，不能在提交/查询时回头读最新检查项配置。

### 3.2 必会实现入口

| 责任 | 真实文件/类 |
| --- | --- |
| 点位/检查项/计划接口 | `PointController`、`ItemController`、`PlanController` |
| 任务接口 | `TaskController`：列表、详情、领取、提交 |
| 计划与生成 | `PlanService`、`TaskGenerateService` |
| 领取与提交 | `TaskService.receive`、`TaskSubmitService.submit` |
| 异常转报修 | `AbnormalService.toRepair` |
| DTO | `CreatePlanRequest`、`GenerateTaskRequest`、`TaskSubmitRequest`、`SubmitItemRequest` |
| Web/移动 | `frontend/src/api/inspection.js`、`Inspection*View.vue`；`mobile/src/pages/task/detail.vue`、`api/inspection.js` |

### 3.3 必背：生成任务的处理

计划含执行时间与每日/每周/每月周期。生成时 `TaskGenerateService.generate(planId, planTime)`：

1. 检查计划启用、日期范围、周期和派发方式；手动生成与自动生成共用这些校验，不能绕过周期。
2. 以 Redis `inspection:generate` token 锁避免多实例重复调度；释放锁时校验 token 所有权。
3. 再以 `(plan_id,plan_time)` 唯一约束兜底；Redis 锁失效也不会插两条。
4. 创建 `ins_task` 与完整 `ins_task_item` 快照，在同一事务提交。
5. 默认是“自行领取”时执行人为空；固定人员、设备责任人、部门轮询均只面向启用的巡检员。

### 3.4 必背：领取与提交接口

**领取**：`PUT /api/inspection/tasks/{id}/receive`。仅 `inspector` 角色；`TaskService.receive` 以条件更新将 `0 待领取 -> 1 执行中`。多人同时操作，只有影响 1 行的一方成功，其余 409。

**提交**：`POST /api/inspection/tasks/{id}/submit`，体为：

```json
{
  "submitNo": "客户端固定幂等号",
  "clientSubmitTime": "ISO 8601 时间",
  "offlineFlag": true,
  "items": [{
    "taskItemId": 101,
    "checkResult": 1,
    "checkValue": "数值或文本",
    "remark": "说明",
    "checkTime": "ISO 8601 时间",
    "fileIds": [201]
  }]
}
```

**`TaskSubmitService.submit` 数据处理步骤**：

1. 校验任务存在、状态允许 `1/3 -> 2`、当前用户是执行人；
2. 校验 `submitNo`，如果 HTTP `Idempotency-Key` 同时出现则二者必须一致；
3. 校验是否覆盖全部任务项、是否扫码到正确点位、必拍项是否有绑定文件；
4. 服务器根据快照、上下限重新计算越界异常，绝不相信客户端传来的“正常/异常”结论；
5. 更新任务项，写 `ins_abnormal`，更新任务异常数/完成时间/`submit_hash`，绑定文件；
6. 相同幂等号且相同载荷返回已有结果；相同号不同载荷冲突；事务失败全部回滚。

异常可由 `AbnormalService.toRepair` 调 M04 公开服务生成报修，来源唯一约束防止重复。

## 4. M07：统计分析与看板

### 4.1 边界和数据处理

M07 只读聚合，不修改任务、工单或设备。`stat_equip_daily` 按设备、按日保存事实聚合，避免每次看板都扫全量业务流水。

- `DashboardService.refresh(statDate)` 查询业务事实，按设备 upsert 日统计，计算任务数、完成数、异常数、故障数、停机时长、MTBF、MTTR、健康分，并失效缓存。
- `overview/trend/pareto/ranking/inspectionSummary` 生成总览、趋势、Pareto、设备排行和巡检汇总。
- 日期范围服务端限制最长 365 天；分母为零时返回 0，避免除零。
- 缓存键以 `wjys:dashboard:` 开头，TTL 10 分钟；Redis 不可用时使用带 TTL 的内存实现以利本地/测试，刷新后按前缀失效。
- `DashboardExportService.exportEquipmentRanking` 用 EasyExcel 流式生成 XLSX，不把大数据全部拼成字符串。

### 4.2 指标解释

- MTBF：可运行时间/故障次数；当前代码以日历小时扣停机时长再除故障数，故障数为 0 时返回 0。
- MTTR：总停机分钟/故障次数，故障数为 0 时返回 0。
- 健康分：100 减去故障、停机、异常率等加权惩罚；范围被限制在 0～100。
- Pareto：按故障量降序，计算累计占比，到 80% 为关键项范围。

真实文件：`DashboardController.java`、`DashboardService.java`、`DashboardExportService.java`、`DashboardQueryMapper.java`、`StatEquipDaily.java`、`frontend/src/api/dashboard.js`、`HomeView.vue`。

## 5. M08：移动离线协同

### 5.1 关键原则

移动端只是体验/同步适配层，不再实现第二套巡检、维修、维保规则。服务端 `MobileSyncService` 复用 M03 等公开服务，避免 Web 与 App 产生不同的状态机。

### 5.2 同步链路和文件

- 服务端：`MobileSyncController.java`、`MobileSyncService.java`、`MobileMessageController.java`。
- 接口：`GET /api/mobile/sync/pull`、`POST /api/mobile/sync/push`、`PUT /api/mobile/messages/{id}/read`。
- 移动端：`mobile/src/repositories/storageRepository.js`、`syncQueue.js`、`photoRepository.js`，以及 `api/sync.js`、任务详情页。

```text
pull 任务快照/消息增量 → 原子写本地快照和 cursor
离线填写 → 保存草稿 → 生成固定 submitNo → 入同步队列
联网 → 照片上传到私有目录对应文件 → 回写 fileId → 按队列 push
confirmed → 保留期后清队列/照片；409 → 人工处理；5xx/网络 → 退避重试
```

pull 用 `(createdTime,id)` 组合游标，兼容旧 `lastSyncTime`；push 批次逐条返回 `confirmed/conflict/rejected/retry`，单条失败不阻塞其它独立任务。照片上传成功并完成业务绑定前不得删除，重试不能换新的幂等号。

## 6. 横切设计必须会讲

| 主题 | 当前实现/答题关键词 |
| --- | --- |
| 事务 | `@Transactional` 包住跨表状态变更：巡检提交、工单验收、库存领用、维保审核；异常抛出即回滚 |
| 并发 | 旧状态条件更新、`version`、库存条件更新；影响行数非 1 即 409 |
| 幂等 | `submitNo` + `submit_hash`；相同请求可安全重试，内容不同拒绝 |
| Redis | 任务生成 token 锁、看板缓存；释放锁校验所有权，缓存可失效 |
| 异常规范 | 400/401/403/404/409 分别表示参数、认证、授权、资源、冲突；统一 `ApiResponse` 含 traceId |
| 前端 | API 层集中，Store 管登录态，路由/按钮权限提升体验，但后端再校验 |
| 部署 | 后端/前端/MySQL/Redis/MinIO 容器化；迁移用 Flyway；不能把真实密钥提交到示例配置 |
