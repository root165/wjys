# 高浩然：M02 设备档案台账 + M04 故障报修与维修复习

> 先阅读 [`00-系统公共能力复习.md`](00-系统公共能力复习.md)。重点是能从设备状态和工单状态两条线讲清真实代码。

## A. 全项目公共复习区（本页内置）

### A.1 小组分工与模块全景

| 成员 | 分工 | 你应能说出的关联 |
| --- | --- | --- |
| 郑亮 | M05 维保、M06 备件 | M05 异常可转 M04 报修；M06 以 M04 工单为领用对象 |
| 高浩然 | M02 设备、M04 报修维修 | 设备是所有业务锚点；M04 是异常到闭环结果的处理中心 |
| 张万健 | M01、M03、M07、M08 与横切设计 | M01 给权限；M03/M05 向 M04 提供异常；M07 只读 M04 结果；M08 适配现场操作 |

```text
M01 权限/审计 → M02 设备台账/状态
                   ├→ M03 巡检（异常） → M04 报修/工单 → M06 备件
                   └→ M05 维保（异常） ───────────────────→ M04
M07 ←────────────── M02~M06 的只读聚合；M08 复用 M03/M04/M05 服务
```

**模块调用的答案：**“M03、M04、M05 都依赖 M02 的公开状态服务；M04 不自己扣库存而调用/暴露给 M06 处理；M07 只查询聚合，不回写业务。这样设备状态、库存和工单规则只有一个权威，避免两个模块各维护一套状态。”

### A.2 架构、数据库和接口公共答案

分层为：Vue/UniApp 用户层 → Controller/JWT/权限/统一异常接入层 → Service/事务/状态机业务层 → Mapper/MySQL/Flyway/Redis/对象文件数据层。DTO 负责请求校验、VO 负责响应、Entity 仅映射表；Controller 不承载状态机。

| 业务域 | 核心表与关键约束 | 数据设计解释 |
| --- | --- | --- |
| M01 | `sys_user`（含 `token_version`）、`sys_role`（含 `data_scope`）及两个多对多关联表 | 权限与数据范围分开，禁用/改密可使旧登录态失效 |
| M02 | `eq_equipment(equip_code unique,status,deleted,version)`、`eq_param`、`eq_status_log` | 主档、扩展参数、状态审计分表；状态履历不能由其它模块跳过 |
| M03 | `ins_task(plan_id,plan_time unique,submit_no unique)`、`ins_task_item`、`ins_abnormal` | 任务和检查项快照支持历史回溯，异常是维修来源 |
| M04 | `wo_repair(source_type,source_id unique)`、`wo_order(repair_id unique,version)`、`wo_order_log` | 报修与执行工单分离，每个动作可审计 |
| M05/M06/M07 | `mt_plan/mt_record`、`wo_spare/wo_spare_record`、`stat_equip_daily(stat_date,equip_id unique)` | 分别支撑预防维护、库存流水、按日只读统计 |

统一 JSON 是 `code/message/data/traceId`；400 参数错误、401 未认证、403 越权、404 不存在、409 重复/并发/非法状态。时间传 ISO 8601，金额 `BigDecimal`，所有库变更走 Flyway。

### A.3 必须共同掌握的流程与保障

1. 巡检计划生成任务时使用 Redis token 锁和数据库唯一键双保险，并快照检查项；提交用 `submitNo + submitHash` 幂等。
2. 异常经来源唯一约束转报修，报修受理创建工单；M04 改设备状态只能经 M02；备件领用在 M06 用库存条件更新。
3. 移动端先草稿/队列，固定幂等号；上传成功绑定后才允许清照片。统计刷新按日 upsert 并清 10 分钟缓存。
4. 所有跨表写入用 `@Transactional`；旧状态/库存放到 SQL `WHERE` 条件中，影响行数不是 1 则 409。

## 1. 我的模块定位与重要性

- **M02** 是设备主数据和状态的唯一权威来源：分类、设备、参数、二维码、状态履历均在这里管理。
- **M04** 将故障从报修到验收处理成可追踪的状态机：受理、派工、接单、完工、验收/退回均留日志。
- 设备是全系统锚点。M03 巡检异常和 M05 维保异常都会进入 M04；M04 只能经 M02 状态服务变更设备状态；M06 对维修工单登记备件，M07 读取已完成事实。

```text
M01 权限 ─> M02 设备/状态履历 <──── M03 巡检异常
                  ↑       ↑               M05 维保异常
                  │       │                    │
                  └──── M04 报修 → 工单状态机 ─┴─> M06 备件、M07 看板
```

一句话价值：M02 保证“这是什么设备、现在是什么状态”；M04 保证“故障由谁处理、处理到哪一步、结果是否被验收”。

## 2. M02：设备档案与状态控制

### 2.1 表、字段与关系

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `eq_category` | `id,parent_id,category_name,status` | 分类树与启停 |
| `eq_equipment` | `id,category_id,equip_code,equip_name,status,responsible_user_id,version,deleted` | 设备主档；`equip_code` 唯一 |
| `eq_param` | `equip_id,param_name,param_value,unit,sort_no` | 一台设备的可扩展技术参数 |

重点：`version` 和“带旧状态的条件更新”用于并发检测；设备删除为逻辑删除，但只有已报废且无活跃巡检/维修单据才允许删除。

### 2.2.1 M02 关键接口与字段表

| 能力 | HTTP | 输入字段（DTO） | 输出/关键校验 |
| --- | --- | --- | --- |
| 新增/编辑设备 | 设备 `POST/PUT` | `categoryId,equipCode,equipName,model,manufacturer,location,responsibleUserId,purchaseDate,warrantyExpire,description` | `equipCode/equipName` 必填；分类需启用；编码唯一；返回 `EquipmentListVO` |
| 设备列表 | 设备 `GET` | `categoryId,status,keyword,pageNum,pageSize` | 只返回轻量列表，按编码/名称筛选，逻辑删除数据不可见 |

| 删除 | `DELETE /api/equipments/{id}` | ID | 仅已报废，且无活跃巡检/维修单据；执行逻辑删除 |

### 2.3 设备新增的输入—处理—输出

`POST /api/equipments`（以 Controller 实现为准）接收 `SaveEquipmentRequest`：`categoryId,equipCode,equipName,model,manufacturer,location,responsibleUserId,purchaseDate,warrantyExpire,description`。

`EquipmentService.create` 的处理：

1. 校验分类存在且启用；
2. 用设备编码查询唯一性，冲突返回 409；
3. 建立 `EqEquipment`，初始状态是 `IDLE`，`deleted=0`、`version=0`；
4. 插入主档，在事务边界内返回 `EquipmentListVO`。

详情接口返回 `EquipmentDetailVO`，额外装配参数和状态日志；列表只返回轻量展示字段，这避免列表查询把日志/照片等重对象全取出。

### 2.4 最关键代码：为什么状态变更必须走服务

`EquipmentStatusService.changeStatus` 的逻辑不是简单 `update status`：

1. 将请求状态转为 `EquipmentStatus` 枚举，非法值 400；
2. 查询活动设备；相同状态直接返回，已报废设备拒绝再次变化；
3. 条件更新：`WHERE id=? AND status=旧状态 AND deleted=0`，同时 `version = version + 1`；
4. 影响行数不是 1，说明被其他请求抢先更新，返回 409；
5. 插入 `eq_status_log`，记录来源模块、来源单据和原因；两步位于同一 `@Transactional`。

因此 M03/M04/M05 不允许直接更新设备表：否则设备状态与状态履历可能脱节，或跳过合法转换规则。

### 2.5 二维码与删除异常

- `EquipmentQrService` 生成设备/点位二维码，并在扫码时 `parseAndVerify`；不能信任二维码明文，需防篡改验证。
- 删除前查询活跃巡检任务与维修工单；有未闭环单据返回 409。原因是删除会切断历史/正在执行业务的外键语义。

## 3. M04：报修与维修状态机

### 3.1 表与状态机

| 表 | 关键字段 | 关系 |
| --- | --- | --- |
| `wo_repair` | `equip_id,source_type,source_id,description,reporter_id,status` | 来源可为巡检异常/维保记录；一个报修对应一张工单 |
| `wo_order` | `repair_id,order_no,assignee_id,status,dispatch_remark,finish_*,downtime_minutes,spare_cost,version` | 维修处理主体，关联备件成本 |
| `wo_order_log` | `order_id,action,operator_id,remark,created_time` | 工单流转审计时间线 |

```text
报修：待受理(0) ──受理──> 已派单(1) ──验收完成──> 已关闭(3)
                  └─驳回──> 已驳回(2)

工单：待接单(0) ─接单→ 维修中(1) ─完工→ 待验收(2) ─验收→ 已完成(3)
                                               └退回→ 退回(4) → 维修中(1)
```

### 3.2 必会文件

| 层 | 文件 | 责任 |
| --- | --- | --- |
| Controller | `RepairController.java`、`WorkOrderController.java` | 报修受理/驳回，派工/接单/完工/验收/退回接口 |
| Service | `RepairService.java` | 从异常或维保创建报修、受理、驳回 |
| Service | `WorkOrderService.java` | 派工、接单、完工、验收、退回和工单日志 |
| DTO | `DispatchRequest/FinishRequest/AcceptRequest/RejectRequest` | 每个状态动作的输入字段/校验 |
| Entity | `WoRepair/WoOrder/WoOrderLog` | 三张表映射 |
| 前端 | `frontend/src/api/workOrder.js`、`WorkOrdersView.vue`、`AbnormalView.vue` | 管理端列表、详情、时间线和操作入口 |

### 3.2.1 M04 关键输入输出字段表

| 动作 | 接口 | 请求核心字段 | 写入/响应 |
| --- | --- | --- | --- |
| 异常转报修 | `POST /api/repairs/from-abnormal/{abnormalId}` | 异常 ID | 新建 `wo_repair(equipId,sourceType,sourceId,description,reporterId,status=0)`，返回 `RepairVO` |
| 受理/驳回 | `PUT /api/repairs/{id}/accept`、`reject` | 报修 ID；驳回 `reason` | 受理创建 `wo_order`、报修 `0→1`、写日志；驳回 `0→2` |
| 派工 | `PUT /api/work-orders/{id}/dispatch` | `assigneeId,expectFinishTime,dispatchRemark` | 工单维修人/计划时间/备注，设备转维修中，写日志/消息 |
| 接单 | `PUT /api/work-orders/{id}/start` | 工单 ID | 仅派工维修人；`0→1` |
| 完工 | `PUT /api/work-orders/{id}/finish` | `finishReason,repairPlan,finishResult,downtimeMinutes,fileIds` 等 | `1→2`，保存原因、方案、结果、停机和证据 |
| 验收/退回 | `PUT /api/work-orders/{id}/accept`、`reject` | 验收照片或退回原因 | 成功关闭工单/报修/异常、恢复设备并统计；退回 `2→4→1` |

### 3.3 核心闭环：巡检异常到验收

1. M03 异常通过 `RepairService.createFromAbnormal(abnormalId, reporterId)` 创建 `wo_repair`；先检查异常状态与 `(source_type,source_id)` 唯一性，避免重复报修。
2. 管理员调用 `PUT /api/repairs/{id}/accept`：`RepairService.accept` 创建 `wo_order`、将报修条件更新 `0 -> 1`、记录 `ACCEPT` 日志。并发冲突会返回 409。
3. 管理员 `PUT /api/work-orders/{id}/dispatch` 传维修人、计划完成时间、派工备注；`WorkOrderService.dispatch` 保存派工、日志、消息，并经 M02 转设备为维修中。
4. 指定维修工 `PUT /api/work-orders/{id}/start` 接单；服务端校验当前用户就是被派人员，再条件更新状态。
5. `PUT /api/work-orders/{id}/finish` 传故障原因、维修方案、结果、停机分钟、照片等；工单从维修中到待验收。
6. 验收人调用 `PUT /api/work-orders/{id}/accept`：关闭工单和报修、关闭来源异常、更新设备状态、通知统计。任何一步失败回滚；若验收不通过，`reject` 记录原因并回到维修中。

### 3.4 输入输出和异常题

**派工输入**：`DispatchRequest` 的维修人员、计划完成时间、派工备注；输出 `WorkOrderVO`，包括状态、维修人、结果、停机、成本等。

**完工输入**：`FinishRequest` 的原因、方案、处理结果、停机时长、文件列表。服务端不只存文本，还要求处于正确状态并且操作人有权限。

**典型异常**：

- 同一异常重复转报修：唯一来源约束/服务检查，409。
- 两个管理员同时受理：报修 `WHERE status=0` 条件更新，只有一人成功。
- 不是被派维修工却接单：身份校验，403 或 409（视具体业务异常定义）。
- 已完工又重复完工：状态不允许，409。
- 验收中设备状态更新失败：事务回滚，工单、报修、异常不能出现一半关闭。
- 设备不存在/已删除：404 或业务冲突，不创建悬挂单据。

## 4. 与其他模块的边界

- 对 M03/M05：只接收“来源异常”，不复制巡检或维保提交逻辑。
- 对 M02：维修模块只发出状态变更请求，设备状态与履历由 M02 写。
- 对 M06：工单提供关联 `orderId`；备件模块校验工单状态后扣库存和累计 `spareCost`，M04 不直接扣库存。
- 对 M07：验收完成后提供故障数量、停机时长等事实；看板只读，绝不能修改工单状态。
