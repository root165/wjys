# 维检云枢：系统公共能力复习（全员必读）

> 用途：后期考核带入资料的公共页。内容以当前实现为准；不要把“计划中”说成“已经完成”。每位成员除本模块外，均应能用本页回答全局问题。

## 1. 30 秒系统总述

维检云枢是面向企业设备全生命周期运维的 Web 管理端和 UniApp 移动端协同系统。设备是业务主线：管理员维护设备台账和规则，巡检员在现场执行巡检，发现异常后形成报修与维修工单，维修中可消耗备件，维保记录经审核后归档；统计看板把前述业务单据转成可读指标。系统目标是让“设备状态、任务状态、工单状态和库存变化”可追溯且一致。

## 2. 角色、模块与调用关系

| 角色 | 主要职责 | 不应越权的事 |
| --- | --- | --- |
| 系统管理员 | 用户、角色、菜单、部门、字典、日志 | 不领取、不填写巡检任务 |
| 设备管理员 | 台账、巡检配置/计划、报修受理派工、验收、维保审核 | 不以普通管理员身份绕过现场执行规则 |
| 巡检员 | 移动端领取、扫码、填写检查项、上传照片、提交 | 不管理全局配置或验收他人业务 |
| 维修工 | 接单、维修、完工、登记备件 | 不领取巡检任务 |
| 企业管理者 | 只读查看台账和统计 | 不直接修改业务数据 |

```text
M01 系统/权限 ─┬─> M02 设备台账 ─┬─> M03 巡检 ─> M04 报修与维修 ─> M06 备件
               │                  ├─> M05 维保 ───────────────> M04（异常报修）
               │                  └─> M07 看板（只读聚合）
               └─> M08 移动协同（复用 M03/M04/M05 业务服务，不复制规则）
```

答辩要点：跨模块通过公开 Service 或领域事件调用，不能跨模块直接操作对方 Mapper；否则事务边界和规则会被绕开。

## 3. 分层与真实代码入口

```text
用户层：Vue Web 管理端 + UniApp 移动端
接入层：Controller、路由、JWT 认证、权限注解、统一响应/异常处理
业务层：各模块 Service，状态机、事务、校验、跨模块编排
数据层：MyBatis-Plus Mapper + MySQL/Flyway；Redis/内存缓存；对象文件元数据
```

- 后端遵循 `controller -> service -> mapper`：Controller 接收 `DTO` 并做参数/权限入口，Service 写业务与事务，Mapper 只访问数据。
- Entity 不直接做接口出入参：请求用 `dto/`，响应用 `vo/`，持久化对象在 `entity/`。
- Web 请求集中于 `frontend/src/api/`，登录状态在 `frontend/src/stores/auth.js`；移动端 Storage 统一经 `mobile/src/repositories/storageRepository.js` 和 `syncQueue.js`。
- Flyway 是唯一的数据库变更路径：`backend/src/main/resources/db/migration/V1__system.sql` 至 `V17__inspection_remove_admin_assignee.sql`。已执行迁移不可改写。

## 4. 最关键三条业务闭环

### 4.1 巡检到维修闭环

计划按周期和 `executeTime` 生成任务；任务生成时快照点位/检查项，后续改配置不会篡改历史任务。巡检员领取后提交检查明细，服务端自行判定数值是否越界、照片是否必传。异常写入 `ins_abnormal`，可唯一转为 `wo_repair`，受理后生成 `wo_order`，完成验收后设备状态恢复并进入统计。

重要性：这条链把“现场发现”变为“有责任人、有状态、有证据的维修结果”，避免异常丢失或重复建单。

### 4.2 维修到备件成本闭环

维修工单维修中可领用备件。`SpareConsumptionService.consume` 对每个备件以 `stock_qty >= use_qty` 进行条件更新，成功才写 `wo_spare_record`，再汇总工单 `spare_cost`；撤销写反向流水而不删除历史。

重要性：库存变化和成本可追溯，并以数据库原子条件防止并发超卖。

### 4.3 维保到归档闭环

维保计划生成/约束记录，同计划同日只能一条；提交记录后由管理员审核。通过后记录归档只读且推进下次日期；退回才可重提；异常结果可进入报修。

重要性：把预防性维护与故障维修区分开，避免“保养做了但没有证据、没有后续计划”的断链。

## 5. 三张最该会讲的数据表（以及关系）

| 表 | 核心字段 | 为什么核心 | 主要关系 |
| --- | --- | --- | --- |
| `eq_equipment` | `id,equip_code,equip_name,category_id,status,responsible_user_id,version` | 设备是巡检、报修、维保、统计的共同锚点 | 1 台设备对应多条任务、异常、报修、维保记录、状态日志 |
| `ins_task` | `id,plan_id,task_no,plan_time,assignee_id,status,submit_no,submit_hash` | 承载“一次计划执行实例”和幂等提交 | 1 个任务对应多条 `ins_task_item` 和异常 |
| `wo_order` | `id,repair_id,order_no,assignee_id,status,finish_* ,downtime_minutes,spare_cost,version` | 承载维修状态机、结果、停机和成本 | 由一张 `wo_repair` 受理生成，关联操作日志及备件流水 |

补充：`ins_task_item` 保留设备编码、点位、检查方法、单位、选项等快照；`eq_status_log`、`wo_order_log`、`wo_spare_record` 都是不可随意删除的追溯流水。

## 6. 通用接口契约与异常话术

- 基础路径 `/api`；请求 JSON 为 camelCase，数据库为 snake_case。
- 成功响应：`{code:200,message:"success",data:...,traceId:"..."}`；列表使用 `pageNum/pageSize`，返回 `list/total/pageNum/pageSize`。
- 写接口必须经过后端的认证、按钮权限与数据范围校验，前端隐藏按钮不是安全边界。
- 400：字段、枚举、日期范围等参数错误；401：未认证或 Token 失效；403：已登录但无权限；404：资源不存在；409：重复提交、唯一约束、非法状态或并发冲突。
- 时间以 `Asia/Shanghai` 解释、ISO 8601 传输；金额用 `BigDecimal`。

可直接答：**“发生并发时我们不是先查后改，而是更新时附带旧状态/库存条件，影响行数不是 1 就返回 409；所有跨表写入放在 `@Transactional` 中，因此任一步失败会回滚。”**

## 7. 异常、一致性与安全的实现点

| 风险 | 当前处理 |
| --- | --- |
| 两人同时领取任务 | `TaskService.receive` 条件更新 `0 -> 1`，失败返回 409 |
| 同一计划重复生成 | Redis token 锁 + `(plan_id, plan_time)` 唯一约束双保险 |
| 离线重试重复提交 | 固定 `submitNo`/`Idempotency-Key` 与 `submit_hash`；相同载荷返回既有结果，不同载荷冲突 |
| 检查项造假/漏拍 | 服务端重新计算阈值异常；必拍项必须有绑定文件 |
| 库存超卖 | `stock_qty >= use_qty` 原子条件更新，流水与成本汇总在同一事务 |
| 设备状态被随意改 | M03/M04/M05 必须调用 `EquipmentStatusService`，并写 `eq_status_log` |
| 登录态失效 | BCrypt 密码校验、JWT、刷新轮换；禁用/重置时递增 `token_version` |
| 文件泄露 | 表中保存稳定对象键/校验信息，不持久化临时下载 URL；文件先上传后绑定 |

## 8. 非功能性需求：建议这样回答

1. **安全性与可审计性**：RBAC 控制菜单/按钮/接口，后端 `@PreAuthorize` 是最终边界；操作日志记录关键动作，敏感信息不写日志；设备和工单状态变化均有流水。
2. **可靠性与一致性**：状态机采用条件更新，跨表写入用事务，移动端队列保留幂等号，库存扣减原子化；网络恢复后逐条同步，单条失败不阻塞独立任务。
3. **性能与可用性（可作为补充）**：看板使用按日聚合表 `stat_equip_daily`，查询使用 10 分钟 Redis/内存 TTL 缓存；列表分页且 `pageSize` 限制为 200；移动端离线保存快照和草稿。

## 9. “新增一个角色/模块怎么办”通用答题模板

以新增“外部维修供应商”为例：

1. 先确定职责：只能看到分配给本人的工单、接单和完工，不能验收或看其他部门数据。
2. M01：`sys_role` 新增角色，`sys_menu/sys_role_menu` 配权限，数据范围限制本人；若需要供应商档案，再新增供应商表并关联用户。
3. M04：`wo_order` 增加供应商关联或建立工单-供应商关系表；Flyway 新增迁移，不改旧迁移。
4. 接口：增加派给供应商、供应商待办查询等 DTO/VO/Controller/Service；所有查询落实数据范围。
5. 前端/移动端：增加菜单、路由、API 和状态展示；复用既有工单状态机，不复制一套流程。
6. 测试：越权读取、重复派工、供应商禁用、历史数据迁移与回滚场景。

## 10. 高频追问速答

**为什么任务要快照检查项？** 计划是规则，任务是历史执行实例；不快照会导致以后修改检查项时历史结果被重新解释。

**为什么不直接删备件领用记录？** 流水承担审计和成本追溯；撤销用反向流水才能保留“发生过又撤销”的事实。

**为什么看板不直接查所有业务表？** 日统计降低聚合成本、固化口径、便于缓存；看板只读，不能反向修改业务单据。

**当前限制是什么？** M08 的 APK/AAB、杀进程、弱网及离线照片需要真机验证；真实 MySQL/Redis/MinIO 的完整联调仍属于环境门禁，不能声称已经完成。
