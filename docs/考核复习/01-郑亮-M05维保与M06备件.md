# 郑亮：M05 维保管理归档 + M06 备件管理复习

> 必须先掌握 [`00-系统公共能力复习.md`](00-系统公共能力复习.md)。本页以“能对着代码讲清实现”为目标。

## 1. 我的模块定位与重要性

- **M05 维保**负责预防性维护：计划、执行记录、审核、归档和异常转报修。它避免设备只在坏了以后才处理。
- **M06 备件**负责维修过程中的备件主数据、预警、库存调整、领用、反向流水和工单成本。它保证维修既能落地又能核算。
- 两者都依赖 M01 权限和 M02 设备；M05 的异常进入 M04，M06 由 M04 工单触发；M07 读取它们的结果做统计。

```text
M02 设备 ─> M05 维保计划/记录 ──异常──> M04 报修/工单 ─> M06 领用/流水
     ↑           │ 审核归档                              │
     └────状态服务┴─────────────────────────────────────┘
                                      ↓
                              M07 统计（只读）
```

回答“为什么重要”：维保让故障前移；备件将维修、库存、费用统一成可追溯闭环。二者分别保障设备可靠性和维修可执行性。

## 2. M05：维保的实现链路

### 2.1 状态、表和关系

- 表：`mt_plan`（计划）与 `mt_record`（记录），迁移为 `V10__maintenance.sql`。
- 计划关联设备 `equip_id`；一条计划可有多条记录；同一 `plan_id + maintain_date` 有唯一约束，防止同日重复记录。
- 记录状态：`0 待审核 -> 1 已归档`，或 `0 -> 2 已退回 -> 0 待审核`。**已归档永远只读，不能修改/重提。**
- 设备状态不能在维保模块直接 SQL 更新，必须通过 `EquipmentStatusService` 写设备状态与 `eq_status_log`。

### 2.2 核心代码入口

| 责任 | 文件/类 | 应讲出的实现点 |
| --- | --- | --- |
| 接口入口 | `module/maintenance/controller/MaintenancePlanController.java`、`MaintenanceRecordController.java` | Controller 接收 `@Valid` DTO，调用 Service，不写状态机 |
| 计划逻辑 | `MaintenancePlanService` | 新增、更新、启停计划；校验设备、周期和日期 |
| 记录逻辑 | `MaintenanceRecordService` | `submit/audit/resubmit`，全部跨表写入在事务中 |
| 请求 DTO | `SaveMaintenancePlanRequest`、`SaveMaintenanceRecordRequest`、`AuditMaintenanceRecordRequest` | 解释请求字段与后端校验 |
| 实体 | `MtPlan`、`MtRecord` | 对应 `mt_plan`、`mt_record` |
| 前端 | `frontend/src/api/maintenance.js`、`frontend/src/views/MaintenanceView.vue` | 页面经 API 层请求，展示计划/记录/审核 |

### 2.3 一次“提交—审核—归档”的输入、处理、输出

**输入（提交记录）**：计划 ID、维保日期、执行人、结果/说明、异常说明、照片 `fileIds` 等，以 `SaveMaintenanceRecordRequest` 为准。资料中不要虚构字段，考前直接打开 DTO 对照。

**处理步骤（对应 `MaintenanceRecordService.submit`）**：

1. 校验计划存在且可执行，校验设备/日期及同计划同日唯一性；
2. 创建 `MtRecord`，保存执行结果和文件关联；
3. 如业务需要，将设备转为保养状态必须调用 M02 状态服务；
4. 如记录结果是异常，调用 M04 `RepairService.createFromMaintenance` 创建来源唯一的报修；
5. 任意一步失败抛出业务异常，`@Transactional` 回滚，不能留下“记录成功但报修/状态失败”的半成品。

**输出**：`MaintenanceRecordVO`，包含记录 ID、计划/设备关联、状态、审核信息等展示字段；统一外层 `ApiResponse`。

**审核处理（`audit`）**：审核通过以条件状态更新 `0 -> 1`，推进计划 `next_date`；审核退回 `0 -> 2` 并保留原因。再次提交仅允许 `2 -> 0`。

### 2.4 M05 异常题答法

- 同计划同日重复提交：唯一约束/服务校验，返回 409，不产生两条记录。
- 已归档记录修改：非法状态，返回 409，保证归档档案不可篡改。
- 审核与下次日期更新中途失败：同一事务整体回滚。
- 维保异常重复转报修：M04 按 `source_type + source_id` 唯一约束拒绝重复。
- 计划停用：阻止新的执行记录；历史记录仍保留审计价值。

## 3. M06：备件的实现链路

### 3.1 状态、表和关系

- 表：`wo_spare`（备件主数据，含编码、名称、规格、库存、预警阈值、单价、状态）与 `wo_spare_record`（领用/撤销流水）；迁移为 `V9__spare_inventory.sql`。
- `wo_spare_record` 关联 `order_id` 与 `spare_id`，一张维修工单能产生多条流水；`wo_order.spare_cost` 是工单备件成本汇总。
- 首期边界：不实现采购/入库全流程；初始库存和调整必须受审计权限约束。

### 3.2 核心代码入口

| 责任 | 文件/类 | 应讲出的实现点 |
| --- | --- | --- |
| 主数据/预警/调整 | `module/spare/service/SpareService.java` | `page/create/update/alerts/adjustStock`；数量、状态、价格校验 |
| 工单领用 | `SpareConsumptionService.java` | `consume` 条件扣减、写流水、汇总成本；`reverse` 写反向流水 |
| Mapper/实体 | `WoSpareMapper/WoSpareRecordMapper`，`WoSpare/WoSpareRecord` | 主数据与不可删除流水分离 |
| 接口 | `SpareController.java`、`SpareConsumptionController.java` | `/api/spares` 和 `/api/work-orders/{orderId}/spares/*` |
| 请求 DTO | `SaveSpareRequest`、`AdjustStockRequest`、`ConsumeSparesRequest`、`SpareUseRequest` | 输入是主数据、调整数/原因、工单领用明细 |
| 前端 | `frontend/src/api/spare.js`、`frontend/src/views/SpareView.vue`、工单页面 | 列表、预警、库存调整、工单领用 |

### 3.3 核心接口：工单领用备件

`POST /api/work-orders/{orderId}/spares/consume`

**输入**：路径 `orderId`；请求体 `ConsumeSparesRequest`，内部是备件 ID、领用数量等 `SpareUseRequest` 明细。每项必须为正数，不能传零或负数。

**数据处理步骤（`SpareConsumptionService.consume`）**：

1. 查询并校验工单存在、处于允许领用的状态；
2. 对每项校验备件存在、启用、数量合法；重复备件的语义是“追加”，不是静默覆盖；
3. 执行带条件的更新：`stock_qty = stock_qty - use_qty WHERE id=? AND stock_qty >= use_qty`；
4. 影响行数不是 1，说明库存不足或被并发修改，抛 409；
5. 插入 `wo_spare_record`，保存数量、单价、金额、操作人及关联工单；
6. 汇总该工单所有有效流水，更新 `wo_order.spare_cost`；整个过程一个事务。

**输出**：领用后的流水/成本展示数据。撤销接口为 `POST /api/work-orders/spare-records/{recordId}/reverse`，只允许写相反方向的流水并回补库存，**不删除原流水**。

### 3.4 M06 异常题答法

- 两人同时领最后一个备件：不是先查询再扣减，而是 SQL 条件更新；只有一个请求影响 1 行，另一个 409，所以不会超卖。
- 领用后流程被取消：用反向流水回补，保留审计轨迹。
- 停用备件/库存不足/数量非正：参数或状态校验失败，拒绝写库存和流水。
- 金额为什么不用 double：单价、领用金额和工单成本均应 `BigDecimal`，避免浮点精度错误。
- 写流水后汇总成本失败：同事务回滚，库存与流水也恢复，避免账实不一致。

## 4. 与其他模块如何衔接（粗略但必须会说）

| 外部模块 | 我方调用/被调用 | 说法 |
